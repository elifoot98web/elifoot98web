# Estudo de UI/UX do Multiplayer + Plano de Melhorias

> **Status:** Phases 1–3 shipped. Phases 4–5 not started.
> As-built deviations are recorded under each phase in §4; where they conflict with the
> prose above them, the as-built notes win.
>
> **Decision §3(b) was reversed in practice.** The study recommended one overlay panel at
> every breakpoint. That shipped, was tested on a phone, and was wrong: on a 390x844
> viewport it left all 496px of letterbox margin empty while overlaying a 253px panel on
> the game. Phase 2 is now DOCKED — the letterbox margin is a free docking budget, because
> a 4:3 frame in a non-4:3 box always leaves slack on one axis and spending it costs the
> canvas nothing. Read §4 Phase 2 "As built" before trusting §3(b).

## 1. Where it stands

The multiplayer feature is functionally complete and architecturally sane: a spectator can receive the host's canvas over WebRTC, move a shared cursor, chat, and see a roster with real latency numbers. All of the hard parts work. What does not work is everything *around* the pipe.

There is one through-line, and it explains findings that look unrelated: **the multiplayer state exists in the services but is never made ambient.** `MultiplayerService` knows the room name, the role, the peer list, the latency, and publishes a `GameState` — and the host page subscribes to none of it. `GamePage` tracks a local `isStreaming` boolean and nothing else (`src/app/pages/game/game.page.ts:41`), so the host UI can express exactly two states, "on" and "off". Every other fact the user needs is parked behind an overlay: the room code lives in a dismissible alert (`game.page.ts:764-780`) and a popover subtitle (`game.page.html:44`); presence lives in a modal reached from a 13-item popover; connection health lives in that same modal and is stale-green when it matters most; and the chat — the one surface that is docked and always visible — carries only user text. The guest's `ion-title` is the hardcoded string `Multiplayer` (`join-game.page.html:6`). A host mid-match cannot answer "is anyone watching?", "what code do I read out?", or "am I still live?" without leaving the game.

The second half of the same story: **because nothing is ambient, every event has to be reported by a blocking dialog** — seven distinct Ionic overlay types across the feature — and the one channel that could carry them cheaply (the transcript) is unused for system events.

Genuinely broken, not merely unpolished:

1. **Below 600px, a *collapsed* chat sidebar eats half the screen.** `.chat-sidebar-flex` keeps its base `height: 100%` (`src/global.scss:134-145`) while the container flips to `flex-direction: column`, so a zero-width sidebar has the same flex base size as the game and both shrink to 50%. This hits every phone user who starts or joins a room, chat closed, and accounts for most of the reported "strange UI on mobile".
2. **The room lifecycle has a zombie state.** `leaveRoom()` never awaits `room.leave()` (`multiplayer.service.ts:68`), and trystero returns the still-tearing-down room object for the same appId+roomId (`@trystero-p2p/core/dist/strategy.mjs:79`; the registry entry is deleted only after `leaveAction.send('')` plus a hard 99 ms wait, `room.mjs:70-78`). A fast retry on the same code silently hands the app a dead room. Nothing errors.
3. **Host election is a coin flip.** `claimHost()` is a 3 s broadcast race (`multiplayer.service.ts:149-185`) whose window is the same order as ICE/relay setup: connect fast and both candidates abort ("nobody can host"), connect slow and both succeed ("two hosts, guests get a scrambled room"). Plus a mandatory 3 s of dead time on every legitimate host.
4. **A 2-second WebRTC blip is reported as "o anfitrião saiu" and destroys the room** (`multiplayer.service.ts:122-129` → `join-game.page.ts:162-170`), costing the guest a re-entry of code *and* password, with no grace period and no re-attach path.
5. **Typing a chat message is broken on iOS**, and the send button's `[disabled]` is bound to a template ref with no input binding (`chat.component.html:23`), so Enter can silently drop a message until an unrelated zone tick runs change detection.
6. **Pasting the share link into the code field cannot work** — and not for the reason it looks like: `maxlength="24"` (`room-setup-modal.component.html:33`) truncates the paste before any parser could see `room=`.
7. **The installed PWA starts at `/#/game`** (`src/manifest.webmanifest`) and `/game` has no exit, so spectator mode is unreachable for the users who installed the app.

**Fixed since this was written (Phase 1):** items 2 (zombie room), 3 (host election), 6
(pasted share links), and the `[disabled]` half of item 5. The `.win9x-*` kit named below
is now extracted to `src/theme/_win9x.scss` and loaded globally. Still open: items 1 and
the iOS-keyboard half of 5 (Phase 2), item 4 (Phase 4), item 7 (Phase 5).

Merely unpolished, but visible: the chat is modern-flat WhatsApp bubbles next to a 1998 Windows 3.1 canvas; the Win9x design kit exists and is convincing but is component-scoped to `omatic-modal.component.scss`, so nothing can reuse a token of it; the roster is a stock Ionic list where an MSN contact list is already fully backed by data.

## 2. Findings by dimension

### 2.1 Retro visual identity (Win9x / MSN Messenger)

**[high] The Win9x vocabulary is trapped in one component and cannot be reused.**
`.win9x-element-border`, `.win9x-element-bevel`, `.win9x-outer-window`, `.win9x-modal-container`, `ion-toolbar.win9x-titlebar`, `ion-content.win9x-modal-content`, `.win9x-select`, `.win9x-input`, `.win9x-button` (+ `:active`, `:focus`, `.button-disabled::part(native)`) all live in `src/app/pages/game/components/omatic-modal/omatic-modal.component.scss:1-142` with emulated encapsulation, and every colour is a repeated literal with the font stack re-declared five times (lines 42, 61, 85, 99, 113) in two different fallback chains. Any second retro surface must copy 140 lines or invent its own greys.
**Do:** extract to `src/theme/_win9x.scss` with `:root` tokens (`--win9x-face`, `--win9x-shadow`, `--win9x-field`, `--win9x-titlebar-bg`, `--win9x-font`, …) and pull it in as the **first** statement of `src/global.scss` via `@use './theme/win9x' as *;` — legal precisely because `@use` must precede other rules, whereas a trailing `@import` after the eight Ionic imports is the deprecated path. Qualify moved rules as `ion-button.win9x-button` / `input.win9x-input` to recover the specificity lost with the `[_ngcontent]` attribute. **Keep local:** lines 46-48 `.buttons-padding-end` and especially 50-56 `ion-toolbar ion-button` — that selector is unqualified and would restyle toolbar buttons on main, game and join. Document two preconditions in the partial: `.win9x-button` only reads as Win9x on an `ion-button` with `fill="clear"` (shadow-encapsulated `.button-native` otherwise paints over the host), and split the select into `.win9x-select` (`color:#000`) and `:disabled` (grey) — omatic's is a disabled fake. Bonus: moves ~3.6 kB out of a 3,623-byte file measured against a 4 kB `anyComponentStyle` error budget.

**[high] The chat panel has zero Win9x chrome, and rebuilding it fixes a real bug.**
`chat.component.html:1` is a bare `.chat-panel` with two children; the compose row is `background:#fff` + `border-top` (`scss:89-98`), the field a `border-radius:1.2em` pill, the send control a flat Ionic green `ion-button`. There is no titlebar, no room context, no status area. Side by side with the Cheat 'O Matic window they look like two different applications, and the chat is what the user stares at all session.
**Do:** four bands, keeping `:host`/`.chat-panel` (`scss:6-20`) byte-identical and still avoiding `ion-content` (the comment at `scss:1-5` documents why): a plain-`div` titlebar (**not** `ion-toolbar` — it drags in min-height and safe-area padding) reading `ELI-QK4T · 3` with `min-width:0; overflow:hidden; text-overflow:ellipsis` and a `win9x-button` [X]; the transcript keeping `flex:1 1 auto; min-height:0; overflow-y:auto` and gaining `win9x-element-bevel` + `#fff`; a compose row on the face colour with a bevelled `input.win9x-input` and a native `<button class="win9x-button">Enviar</button>`; a status bar carrying the `env(safe-area-inset-bottom)` padding moved off the compose row. Participant count comes from a new `participantCount$ = playerList$.pipe(map(p => p.length))` — **not** from `ChatComponent.players`, which is deliberately sticky (`chat.component.ts:75-81` never deletes departed players) and would over-count. The guest room code needs exposing: `join-game.page.ts:25` is `private roomId`. Same commit, flagged as a bugfix: swap the template ref for `[(ngModel)]` (FormsModule already imported, `core-components.module.ts:12`) so `[disabled]` tracks the field — today it stays stale, and because that is the form's default submit button the browser blocks implicit Enter submission while it is stale-disabled. **Hard dependency on the partial:** `chat.component.scss` is already 2,023 bytes against a 2 kB warning / 4 kB error budget, so duplicating tokens locally would fail `npm run build`.
**Mobile budget caveat:** titlebar + statusbar + compose is ~90 px of chrome, ~120 px once coarse-pointer 44 px floors apply, against a 220 px drawer. Either drop the status bar below 601px (fold the typing indicator into the titlebar) or raise the open panel to `min-height: 260px` there.

**[high] Bubbles are the wrong metaphor and waste 20% of a 320px sidebar.**
`chat.component.html:4-13` renders `max-width:80%` 1.2em bubbles in `#d2f8d2`/`#f1f1f1`, with the sender name blanked for own messages and repeated on every consecutive line. In a 320 px sidebar that leaves ~200 usable px, so ordinary pt-BR sentences wrap after four words; in the 220 px mobile drawer the repeated name eats a third of the vertical space. MSN never had bubbles — it had a white transcript with coloured `Nome diz:` lines.
**Do:** full-width `.chat-line`, no radius, `padding:1px 4px`; bold `{{ nome }} diz:` header in the sender's colour, own messages included (self is in the roster via `setLocalPlayer`, `player-info.service.ts:73`), with an explicit `Você diz:` marker since `MULTIPLAYER.PLAYER_COLORS` has 8 entries and nothing enforces uniqueness; group consecutive messages from the same `senderId` within 60 s by building a view model in the `messages$` pipe (`chat.component.ts:30`), carrying `message.id` so `trackBy` survives. `#ffe119` and `#42d4f4` are unreadable on white, so **add** `ColorHelper.darkenForText(hex)` — the existing helper exposes only `getCSSFilterFromColor`, an SPSA optimiser running up to 3,500 iterations, and must never be called from a template expression on the game page where CD fires every 1.5 s. Compute `textColor` once per player in the view model. `.chat-empty` moves from `#e8f5e8` (chosen for the green gutter) to `var(--win9x-shadow)` italic; keep `Nenhuma mensagem ainda. Diga oi!`.

**[high] Win9x defaults would ship 11px grey-on-grey and 16px hit targets unless the floors are written in.**
Nothing in `src/` has a `prefers-reduced-motion` block (verified), against 300 ms width transitions (`global.scss:125,135`) and a `scale(8)` `ping` (`228-234`). `.win9x-button` declares `padding:0 12px` with no min-height, and the only focus affordance is `outline:1px dotted; outline-offset:-4px`.
**Do:** bake into the partial — 12 px minimum body text, always `#000` on `--win9x-field` inside the transcript, grey-on-grey **only** for disabled or inactive chrome (never transcript text, compose field or participant names); `min-height:23px` on `button.win9x-button` only (Ionic controls host height itself), plus `@media (pointer: coarse) { min-height/min-width: 44px }` paired with the drawer-height increase above; expand the titlebar [X] hit box with padding, not by scaling the glyph. **Focus, corrected:** keep `ion-button.win9x-button:focus` (optionally `.ion-focused`) for Ionic buttons and use `:focus-visible` only for native `button`/`input` — `ion-button` is `encapsulation: "shadow"`, the focused element is the inner `.button-native`, and `:focus-visible` does not match the host, so a `:focus-visible`-only rewrite would silently *remove* the keyboard focus ring from the cheat modal. One global reduced-motion block zeroing the two transitions, the `ping`, and any future toggle flash.

**[medium] No join/leave system lines: the transcript never says who arrived or left.**
`MultiplayerChatService` only ingests `sendMessage`/`chatMsg` (`multiplayer-chat.service.ts:28-61`); peer arrival is known (`player-info.service.ts:26`) and departure still has the `PlayerInfo` (`:82`), but nothing renders it. With the roster behind a modal, arrivals and departures are invisible.
**Do:** `kind: 'chat' | 'system'` as a **required** literal set in `sendMessage`/`addSystemMessage` — optional would be `TS2411` against the inherited `[key: string]: JsonValue` index signature under `strict: true`, and `msg.kind === 'system'` is already false for `undefined`, so it stays wire-tolerant with older peers. Synthesise locally per peer (never broadcast, or everyone sees N duplicates). Emit the join line from the **ident** handler (`onPeerJoin` has no name yet) and the leave line from the leave handler — which requires **moving `setupChatService()` above `setupPlayerInfoService()`** in `joinRoom`, because today chat is set up at line 134, *after* `removePlayer` is registered at 233, and handlers fire in registration order, so a leave line would print `undefined saiu da sala`. Copy: `{{nome}} entrou na sala.`, `{{nome}} saiu da sala.`, `Você entrou na sala {{código}}. Você está assistindo como espectador.` **Drop the HOST_LEFT line** — it is unreachable: `setState(HOST_LEFT)` makes `JoinGamePage` call `leaveRoom`, which runs `chatService.clear()` in the same turn, and the sidebar is inside the `ion-hide` subtree by then. The existing card copy already says it. Badge: also advance `readMessageCount` when a system line lands while hidden, otherwise `unread = messages.length - readMessageCount` bumps regardless of how the template renders it.

**[medium] The sidebar gutter is Ionic green and the toggle is a flat yellow pill.**
`.chat-sidebar-flex` paints `--ion-color-primary-shade` (`global.scss:139`, actually `#047204`, so the `#005500` fallback never applies) with a soft 8 px blur; the toggle is `ion-button color="secondary"` with a round badge. Once the chat is a grey Win9x window these two break the illusion.
**Do:** face colour on the gutter; put the hard `border-left: 2px solid var(--win9x-shadow)` on `.chat-panel` **inside** the clipped sidebar, not on `.chat-sidebar-flex` — Ionic sets `* { box-sizing: border-box }`, and `width:0` + 2 px border renders a permanent 2 px sliver beside the canvas; in column mode use `border-top`. For the toggle, drop `color="secondary"` and add `fill="clear"` (or `--background: var(--win9x-face)`) alongside `win9x-button` plus the `--ripple-color/--background-hover/--background-focused: transparent` trio — the class alone changes nothing, because the shadow `.button-native` paints `--background` over it. Square the badge. Keep the toggle where it is (`global.scss:153-157` correctly explains why). Leave room left of the titlebar [X] for a future control-handoff affordance.

**[medium] Retro scope, and the roster as an MSN contact list.**
Two visual systems already coexist. `RoomSetupModalComponent` and `ParticipantsModalComponent` sit on the modern side (`ion-list`, stacked `ion-input`, 40 px round swatches, round dot with `box-shadow`), so the dialog immediately preceding a retro chat is flat Ionic.
**Do:** convert both to the omatic skeleton; swap `ion-input` for `input.win9x-input` (safe — `isValid` reads plain fields, `[(ngModel)]` keeps working; carry `maxlength`, `required`, `autocapitalize`, `type="password"` and a real `<label for>` by hand); square the swatches to 44 px, selection = pressed-in bevel rather than `transform:scale(1.15)`; verify eight swatches wrap at 320 px. **The `--height` treatment needs a fifth file:** `multiplayer-ui.service.ts:26-29,37` creates both modals with **no `cssClass`**, so `.omatic-modal { --height: 480px }` has nothing to hook — add `cssClass: 'win9x-modal'` there. Re-render roster rows as `.msn-contact-row`: square 10 px status dot, bold name with `(anfitrião)` as plain text instead of an `ion-badge`, latency right-aligned in a statusbar cell, host-first sort preserved (`participants-modal.component.ts:26-29`). **`latencyColor()` returns Ionic colour *names*** (`'medium' | 'success' | 'warning' | 'danger'`), so binding it to `background-color` yields a transparent dot — map to a class or `var(--ion-color-{name})`. Treat the dot as decoration and keep `N ms` as the source of truth; do not invent MSN presence states ("ausente") a 400 ms guest does not have. Extract one presentational `app-participant-list` declared in `CoreComponentsModule`, reused by the modal and (≥601px only, default collapsed) as a contact strip in the chat.

**[low] Typing indicator, emoticons, fonts.**
`TYPING: 'typing'` is legal — the `≤12 characters` comment at `constants.ts:79` is stale after the trystero upgrade; the real limit is 32 bytes (`action-wire.mjs:4`). Export `BaseMessage` (currently non-exported) and declare `interface TypingMessage extends BaseMessage { typing: boolean }`; cache the action (`makeAction` is idempotent per namespace but caching is cleaner) and **broadcast rather than target**, since targeted `send` rejects with `no active peer with id …` and would surface as unhandled rejections on every peer churn. `.catch(() => {})` regardless. 4 s expiry map so a closed tab cannot stick. Render in the status bar, never the transcript (it would fight `scrollToLatest`, `chat.component.ts:67-73`): `{{nome}} está digitando...` / `{{a}} e {{b}} estão digitando...` / `Várias pessoas estão digitando...`. Needs the ngModel swap to have anything to hook.
Emoticons: a pure `MsnEmoticonPipe` in `CoreComponentsModule` substituting `:)` `:-)` `=)` `:(` `:D` `=D` `;)` `:P` `(y)` `(l)` at render time only, on word/whitespace boundaries so `2:1` and URLs survive, wire format untouched. Never `[innerHTML]`.

### 2.2 Mobile layout and the stream jump

**[critical] Collapsed sidebar takes 50% of the column below 600px.**
`.chat-sidebar-flex` has `height: 100%` with no override in the ≤600px block, which only touches `height` inside `.chat-open` (`global.scss:184-199`). In column direction `flex-basis: auto` resolves to that height, matching `.game-stream-container`; both have shrink 1 and an automatic minimum of 0, so it is an even split. The host mounts the sidebar the moment `isStreaming` (`game.page.html:167`); the guest has **no `*ngIf` at all** (`join-game.page.html:93`), so a guest gets a half-height game before touching the chat.
**Do:** drive both panes off the flex main axis, which is direction-agnostic. `.game-stream-container { flex: 1 1 0 }`; `.chat-sidebar-flex { flex: 0 0 0; align-self: stretch; overflow: hidden }` with `width`/`height` **removed entirely** — `align-self: stretch` supplies the cross size in both directions, which is what the proposal's "just delete the calc()s" version got wrong (it would collapse the *open* sidebar to zero width in column mode). `.chat-open { flex-basis: 320px }`, `@media (max-width:600px) { flex-basis: clamp(160px, 35vh, 300px) }`. Delete `max-height: 60vh` and both `min-width` values, delete the `with-chat` rules *and* the class from `game.page.html:156` and `join-game.page.html:81`. **Caveat before quoting any px arithmetic:** both pages define a component-scoped `.full` on the same div (`game.page.scss:5-9`, `join-game.page.scss:5-9`) with identical specificity to `.game-stream-container.with-chat`, appended to `<head>` after the global sheet — so the `calc()` declarations are probably already inert and flex-shrink is doing the work. Confirm in devtools. The flex-basis model removes the ambiguity, which is the actual defect: two rules computing the same dimension.

**[critical] The toggle jump, traced — and avoidable in full.**
js-dos letterboxes by writing `style.top/left/width/height` on a canvas whose backing store is set only from its frame-size handler (verified in `src/assets/js-dos/js-dos.js`), so on a toggle the canvas *translates* ~85 px and back. Three mechanisms make it read as a bug: in column mode the main size jumps untransitioned (hard one-frame snap); the resize detector fires *after* the container resized, so one frame has new box + old canvas geometry, clipped by `overflow:hidden`; and already-rendered remote cursors keep the pixel `left/top` `CursorRendererHelper` gave them (`cursor-renderer.helper.ts:51-54`) until the next message arrives, so every stationary cursor is wrong after a toggle even though `OverlaySyncHelper` re-aligns the box. On desktop it is worse in a quieter way: the animated `width` on `.chat-sidebar-flex` feeds `flex-basis: auto` frame by frame, so js-dos re-letterboxes ~18 times and the host loses their place in a UI with ~8 px click targets.
**Do:** stop resizing the game surface. Make the chat an absolutely-positioned overlay animated with `transform` only. Two things the proposal omits and both are blockers: `.game-stream-flex-container` (`global.scss:108-115`) has **no `position`** — on the host `.full` does not add one either — so an `inset:auto 0 0 0` panel would dock to the page, not the game surface; add `position: relative`. And the panel needs an explicit `z-index` above 1000, because `.emulator-keyboard` is `z-index:999` (`js-dos.css:225-239`) inside `#game-container`, which is `position:relative; z-index:auto` (`game.page.scss:14-16`) — the same stacking context. Also expose `CursorRendererHelper.repositionAll(overlay)` reading cached `el.dataset.nx/ny` (written next to lines 53-54) and call it at the end of `syncOverlayWithGameCanvas()` (`game.page.ts:913-918`) and `syncStreamContainer()` (`join-game.page.ts:277-285`); leave the deliberate `isSelf` transition guard alone.

**[high] The premise that toggling chat changes stream resolution is false.**
`join-game.page.ts:215-216` and `overlay-sync.helper.ts:1-11` both assert it; the vendored bundle says otherwise, and `canvas.captureStream(30)` (`game.page.ts:745-758`) captures the backing store. This false constraint is what makes the docked-shrink model look mandatory, and it is the strongest argument for overlaying.
**Do:** correct both comments — but not into the opposite error. Wording: *the **captured** track resolution follows the DOS frame size and is independent of the host's layout; the received dimensions can still change on a DOS video-mode change or on WebRTC encoder downscaling, which is why this listener exists.* Keep the video `resize` listener. Skip the participants-modal readout via `getSettings()` on a remote track (not reliably populated); read `videoWidth/videoHeight` off the element if you want it.

**[high] Toggle placement, collisions, and the single entry point.**
`.chat-toggle-btn` is `top:8px; right:8px; z-index:20` while the panel emerges from the bottom on mobile, and it sits directly under the header's overflow button in portrait. More importantly it is the **only** way in: the guest toolbar has participants and leave but no chat (`join-game.page.html:7-14`), and the host popover has share/participants/end but no chat item. The claimed FAB collision is overstated for the *current* placement (the landscape arrow list fans to y≈100-170 against a toggle at y=8-56) — it is a property of the proposed bottom placement, which the proposal already handles.
**Do:** land the redundant entry points first; they are the highest-value part and depend on nothing — an `ion-item` "Chat" with the unread badge in the host popover next to Participantes, and an `ion-button name="chatbubble-ellipses-outline"` in the guest toolbar's end slot. Then anchor the control to the edge the panel comes from per breakpoint (bottom-centre pill on mobile at `bottom: calc(72px + env(safe-area-inset-bottom))`, right-edge grip on desktop) with `z-index: 1000`. The toggle **cannot** be wrapped in the existing `*ngIf="!isVirtualKeyboardShowing"` container (`game.page.html:192` is a sibling of the flex container) — it needs its own `*ngIf="isStreaming && !isVirtualKeyboardShowing"`, and the guest has no emulator and must not inherit that guard at all.

**[high] iOS soft keyboard hides the compose row.**
`.chat-input-row` compensates only for the static notch (`chat.component.scss:89-98`); the viewport meta has `viewport-fit=cover, user-scalable=no` and no `interactive-widget`; the host's `ion-content` is `[fullscreen]="true"` with scrollY defaulting to true, so Safari scrolls it and displaces the emulator, while the guest's `[scrollY]="false"` leaves the input simply unreachable.
**Do:** a small `KeyboardInsetService` writing `--kb-inset: max(0, layoutHeight - visualViewport.height - visualViewport.offsetTop)px` on `document.documentElement` from throttled `resize`+`scroll`, consumed as `padding-bottom: calc(0.4rem + max(env(safe-area-inset-bottom), var(--kb-inset, 0px)))`. **Do not add `interactive-widget=resizes-content`:** it resizes the layout viewport, which resizes `#game-container`, which re-runs the letterbox closure — reintroducing the exact jump this dimension exists to remove, on Android, on every message. One-line partial cure worth taking immediately: set `[scrollY]="false"` on the host while a room is live, so Safari cannot displace the canvas on focus.

**[medium] 70vw at ≤900px, the 220px drawer, and orientation.**
The `70vw` rule exists (`global.scss:174-182`) but both worked examples in the audit are wrong: in landscape the 4:3 canvas is height-limited, so eating width mostly eats letterbox margin (~4% loss under the flex-shrink reading, not "a stamp"), and the claimed 28 px dead strip requires two rules to both be live. **Downgrade to medium.** What is genuinely wrong is that `<600px` *width* catches landscape phones and forces `flex-direction: column`, spending the scarce axis on chat.
**Do:** `@media (orientation: landscape) and (max-height: 600px) { flex-direction: row; .chat-open { flex-basis: min(320px, 38vw) } }`, ordered so it beats the width query (or express the other as `and (orientation: portrait)`); replace `70vw` with `min(320px, 45vw)`. Separately, compact the message row regardless of layout model: single-line meta and `0.35rem 0.6rem` padding fits ~5 messages where ~2-3 fit now.

**[medium] `scaleVideoToContainer()` can be pure CSS; naive `object-fit` would break the overlay.**
`join-game.page.ts:287-308` reads `videoWidth/videoHeight` and `clientWidth/Height`, writes px, forces `objectFit='unset'`, driven by a ResizeObserver — a read-then-write layout pass per frame.
**Do:** `#stream-target { flex: 0 1 auto; align-self: center; width: auto; height: auto; max-width: 100%; max-height: 100%; margin: auto }`. Pin the flex properties explicitly: a replaced flex item with auto main sizes and both max constraints is the case engines have historically disagreed on; verify with the non-4:3 DOS text-mode frame first. **`object-fit: contain` is not equivalent** — the box would include the letterbox bars, and both `OverlaySyncHelper.align` (`offsetWidth/offsetHeight`) and the guest's normalisation (`event.offsetX / target.clientWidth`) would map coordinates over them. Keep the ResizeObserver and the `resize` listener. Treat the `inline-block` wrapper variant as separate later work: it changes the video's offsetParent and breaks `detachStream`/`attachStream`'s assumption that `video.parentElement` is the observed container.

**[medium] js-dos keyboard and the chat both claim the bottom — and the *real* focus bug is the mirror image.**
The geometry and z-index conclusion hold. The "keystrokes swallowed by DOS" rationale does not: js-dos binds key input on its own root (`initKeyEvents` uses `keyboardInputDiv ?? this.root`), and the chat input is outside it. **[medium] Landing page `translateY(-50%)` clips the *top* card unreachably.**

**[low] Guest video has no `touch-action`.**

### 2.4 Host election (host claim)

**[critical] Retrying the same code hands the app a dead room.** See §1. **Do:** keep the load-bearing logic in the service and stop asking call sites to cooperate — `this.leavingPromise = (this.room?.leave() ?? Promise.resolve()).catch(...)` **before** clearing `this.room`, keep `leaveRoom` synchronous (both `ngOnDestroy` sites cannot await, and making it async silently turns them into fire-and-forget with an unhandled rejection surface), and `await this.leavingPromise` as the first statement of the private `joinRoom()`, before the `Already in a room` guard. Add a `joiningPromise` mutex too: `isInRoom` is false during the drain, so two rapid joins can both pass. Drop the "throw if the room object is identical" invariant — once the drain is awaited it is unreachable, and throwing user-facing pt-BR for a 99 ms race is worse than the race. One UX touch: in `JoinGamePage.joinRoom()` set the loader to `Encerrando a sala anterior…` while the drain is pending. Note the honest severity: only that one path is genuinely inside the window (the other retries go through a user-driven modal), which is exactly why it presents as intermittent flakiness rather than a reproducible failure.

**[critical] Delete the 3 s claim race; detect presence, resolve by selfId.**
**Do:** `hostGameRoom()` becomes `joinRoom` → `setupHost(stream)` → `IN_ROOM`, synchronous. Register one request action on **both** roles inside the private `joinRoom()` — `room.makeAction('roleQuery', { kind: 'request', onRequest: () => this.describeSelf() })` (32-byte limit confirmed, so readable names are fine) — plus a `hostAnnounce` message sent once, targeted, from the host's `onPeerJoin`. On the host's `onPeerJoin`, `await roleQuery.request({}, { target: peerId, timeoutMs: 5000 })`; `role === 'host'` is a collision, detected whenever it becomes observable, with no window to miss. **Resolution: the lexicographically greater `selfId` yields** — same comparison, same two strings, both sides always agree, no clock, so mutual abort and split brain are gone by construction. Delete `claimHost()`, `HOST_CLAIM`, `HOST_CLAIM_TIMEOUT`, `HOST_CLAIM_INTERVAL`, `HostClaimMessage`.
Three amendments the design needs. **(1)** Detection is now asynchronous and unbounded in time, so it cannot be reported by throwing from `hostGameRoom()` — and `GamePage` has no `gameStateSubject` subscription at all (the only subscriber in the repo is `join-game.page.ts:59`). Expose a dedicated `hostCollision$` and subscribe to it in `startHosting()`'s existing subscription bag; smaller blast radius than giving `GamePage` a full state machine. **(2)** The loser calls `leaveRoom()` from inside `onPeerJoin` while `onPeerJoinHandlers.forEach` is still iterating — defer with `queueMicrotask` and add an `isLeaving` guard at the top of both fan-outs. **(3)** Wrap the request in try/catch: it throws `disconnected` if the peer vanished between join and request, and `onRequest` must never return `undefined`. State the residual honestly in a comment rather than claiming impossibility: if ICE between the two hosts fails, neither observes the other and two hosts persist (they also cannot poach each other's guests in that state).
Copy — loser: header `Código de sala já em uso`, body `Já existe uma sala em andamento com o código {{código}}. Sua transmissão foi encerrada e quem estava assistindo foi desconectado, mas seu jogo continua aqui.`, buttons `Gerar novo código` / `Fechar`. Winner: `Alguém tentou abrir outra sala com o seu código. Sua transmissão continua no ar.` Add `ROOM_CODE_TAKEN` to `GameState`.
**Do not** ship the tempting micro-fix of moving `setupHost(stream)` before `claimHost()` to kill the 3 s: both candidates would then broadcast video during the window, guaranteeing the scrambled room.

**[medium] The hostClaim echo can ping-pong forever.** `setupHost` replies unconditionally, broadcast, uncaught (`multiplayer.service.ts:198-204`). Two established hosts plus one inbound claim is an unbounded loop at data-channel speed, saturating the channel that also carries chat and cursors. Guests never register the namespace, so every claim they receive accumulates in `pendingActionPayloads['hostClaim']` and is never drained. **Downgrade to medium:** it needs the split-brain state to start, and the console-DoS framing does not hold (the `Room` object is never exposed on `window`; an attacker needs a purpose-built page with appId + code + password). Worth knowing while reading that code: both `claimHost()` and `setupHost()` call `makeAction('hostClaim')` and trystero returns the *same* action object, so `setupHost` **replaces** the detection handler and the `reclaimed` closure is dead from then on. Subsumed by the replacement; if a standalone patch is wanted, reply at most once per peer with `{ target: peerId }` plus `.catch`, and register a no-op handler on guests to drain the buffer. **Do not** simply delete the echo: an established host stops broadcasting after 3 s, so the echo is the only way a late candidate learns a host exists — removing it turns occasional split-brain into guaranteed split-brain.

**[medium] Host identity is self-asserted.** `role: ident.host ? HOST : GUEST` (`player-info.service.ts:26-36`) is trusted verbatim, so any peer can wear the yellow `anfitrião` badge, sort to the top, and — by leaving — trigger a bogus HOST_LEFT that tears down a healthy room for everyone. **Drop the "the ident might be lost" half of the argument:** trystero queues payloads for unregistered types and flushes them on creation (`action-wire.mjs:80-83`), data channels are reliable and ordered, and the handler is registered synchronously before any peer can connect. **Do:** derive host-ness from who actually delivered a video track — expose `hostPeerId$` from `MultiplayerStreamService`'s existing `onPeerStream` handler and wire it in from `MultiplayerService`, not by injecting one service into the other; keep the local role as the badge source for `peerId === selfId` so the host's own device still shows it; answer `roleQuery` with the local ident so late joiners can pull; drop `host` from `PlayerIdentMessage`. Call it **unforgeable-enough**, not authoritative — a crafted client can still `addStream`. The password is the only real admission control (trystero derives the room key from it), so say that in the UI: `Use uma senha se quiser garantir que só quem você convidar entre.`

**[medium] `onJoinError` is never wired, so a wrong password costs 20 s.** `joinRoom(config, roomId)` is called with two arguments (`multiplayer.service.ts:116`); the third callbacks parameter exists in 0.25.3 and reports incorrect passwords, handshake failures and post-SDP connectivity failures. **Do** wire it, and scope the promise honestly on two counts. `details.error` is a plain English **string**, so classification is substring matching and must always fall through to the current 20 s message as its default. And the guest only learns it about half the time: trystero picks the offer leader by `selfId < peerId`, and only the *answering* side fails to decrypt — when the host is the answerer, the **host** gets an unsolicited password error caused by a stranger and the guest still waits 20 s. So: guest-side, push fatal classifications into a `joinError$` the wait races with, but only for peers being waited on, keeping the timeout as fallback; host-side, **never** tear down a healthy broadcast — a toast at most (`Alguém tentou entrar com a senha errada.`). Log the TURN hint so `environment.multiplayerConfig.turnConfig` problems stop looking like user error. Reword rather than delete the comments at `multiplayer-stream.service.ts:22-28` and `constants.ts:92-95`: the "wrong code is indistinguishable from an empty room" half is still true.
Copy: `Senha incorreta para a sala {{código}}. Confirme a senha com o anfitrião.` / `Não foi possível estabelecer a conexão direta com o anfitrião. Tente outra rede (Wi-Fi em vez de dados móveis) ou desative a VPN.`

**[medium] Codes are fine; the field is unvalidated free text.** 32⁴ = 1,048,576 with no modulo bias, ~0.5% birthday collision at 100 concurrent rooms — adequate. But the input accepts 24 free-form characters, `isValid` only requires non-empty, and `normalize()` only trims and `toLocaleUpperCase()`s (locale-sensitive: tr-TR turns `i` into `İ`). "TESTE", "1234", "a" are all valid and highly collidable. **Do:** `isValid()` and `sanitize()` built from `MULTIPLAYER.ROOM_CODE_ALPHABET`/`ROOM_CODE_LENGTH`; strip a leading `ELI-`/`ELI` **before** re-applying the prefix, or a pasted `ELI-ABCD` becomes `ELI-ELIABCD`; `toUpperCase()` not locale — that alone is a bug fix. **Sanitize on `ionBlur` and in `confirm()`, not on every keystroke** through `ngModel`: rewriting the value per keystroke fights `ion-input`'s internal value and jumps the caret to the end, worst on mobile. `maxlength="8"`. Copy: `O código deve ter o formato ELI-XXXX (sem as letras I, O e sem os números 0 e 1).` Keep length at 4.

**[low] Hosting failures are untyped strings.** `hostGameRoom` throws user-facing pt-BR from a service; `game.page.ts:689-693` re-wraps everything into one OK-only `Erro` alert, so a collision, a missing canvas and a relay failure look identical and none offers a next step. **Do:** `MultiplayerError` with a `code`, copy centralised in `MultiplayerUiService` with recovery handlers **passed in as callbacks** (don't let a root service own `window.location.reload()`), and warn that `Recarregar o jogo` discards anything not flushed by `saveGameFileSystem()`. Three delivery channels, not one: `CANVAS_NOT_FOUND`/`CONNECTION_FAILED` thrown synchronously, `ROOM_CODE_TAKEN` on `hostCollision$` (asynchronous), `WRONG_PASSWORD` from the guest's `onJoinError`. Fix the `constants.ts:79` comment to `≤32 bytes (trystero action-wire typeByteLimit)`.

### 2.5 App-wide UX (the parts that gate multiplayer)

**[critical] The installed PWA starts at `/#/game` and `/game` has no exit — spectator mode is unreachable.**
`manifest.webmanifest` `start_url: "/#/game"`; `game.page.html` has no back button and the popover has no exit item, while `join-game.page.html:5` *does* have one. A friend sends an `ELI-XXXX` link, the installed app opens on the solo game, and there is nowhere to type the code.

**[medium] Help never mentions multiplayer, and two FAQ instructions name menu items that no longer exist.**
Zero hits for sala/multiplayer/espectador/hospedar across `manual.component.html` and `faq.component.html`; `faq.component.html:25` says `Baixar Jogos Salvos` where the menu says `Exportar jogos salvos`; `:49-50` says the keyboard button is "na parte superior da tela", which is false in mobile landscape.

## 3. The design decisions to settle first

These gate later phases; each is a decision for the owner, with a recommendation.

**(a) How far does the Win9x/MSN identity spread?**
**Recommendation: "companion windows are Windows 95; the app shell stays Elifoot green."** Convert the chat panel, the roster, the room-setup modal and the multiplayer panel. Do **not** touch the three `ion-toolbar color="tertiary"` page headers, the landing cards, the FAB stack or the popover — navy `#092469` is close enough to `#000080` that the shell and the retro windows read as deliberately related rather than accidental.
Reasoning: the retro treatment needs an explicit boundary or it looks like a mistake, and the green/yellow palette mirrors the game's own pitch-green UI. Also, one audit proposed going further and framing `#game-container` in a bevelled Win9x window with a titlebar reading "Elifoot 98". **Reject that:** the frame must wrap the container (a titlebar child would end up under the canvas, since js-dos sizes the canvas to that box), it costs canvas pixels on the device where they are scarcest, and it buys nothing functional. `MS Sans Serif` also has no `@font-face` anywhere, so on macOS/iOS/Android the whole frame would render in the system sans — acceptable as a wink inside one modal, weak as the app's dominant chrome. (An earlier draft also claimed the frame would change the captured track resolution for every spectator. That is wrong, and §2.2 says so: the captured track follows the DOS frame size, not the host's layout. The rejection stands on the grounds above.)
Forecloses: a full Win95-desktop metaphor; and it means the landing page and the join-game state cards stay flat Ionic, so reversing later means redoing both.

**(b) The mobile chat model: docked sidebar or sheet modal?**
**Recommendation: neither — one absolutely-positioned overlay panel animated with `transform`, at all breakpoints.** Bottom-anchored in portrait, right-edge in landscape and on desktop.
Reasoning: the goal is that `#game-container` never resizes, so js-dos never re-letterboxes and the host's aim in an 8-px-target UI stays stable. The overlay reaches that with plain CSS and no Ionic internals. The `ion-modal` sheet reaches the same goal but needs `expandToScroll: false` (otherwise the compose row is laid out below the screen at every breakpoint under 1), `.ion-content-scroll-host` on `.chat-messages` (otherwise dragging the transcript drags the sheet), gating the docked sidebar out of the DOM (otherwise two `ChatComponent` instances fight over the single `setChatVisible`), and a `private` on the `chatService` constructor parameter on both pages — an L of Ionic-internals coupling that cannot be tested. And overlaying costs spectators literally nothing: they receive the bitmap.
On desktop, occlusion is near-zero in practice because a 4:3 canvas rarely fills a 16:9 viewport — the panel lands mostly on the letterbox margin. Forecloses: the sheet's free drag-to-resize handle (build a grip if wanted) and side-by-side reading without any occlusion on a wide monitor. If the owner wants the true docked sidebar back on very wide screens, gate it behind `@media (min-width: 1200px)` and accept one re-letterbox per toggle — but drop `transition: width` there so it is one re-layout instead of ~18.

**(c) What does "host" mean in the protocol, given a guest can never become one?**
**Recommendation: host = the peer that actually delivered a video track. There is no election.**
Reasoning: a guest has no emulator and cannot serve a stream, so there is nothing to elect — the bully algorithm and every general election are wrong *in kind* here, because they can elect a peer that cannot host. The two real problems are (i) publishing who the host is and (ii) resolving the pathological "two people on one code". Solve (i) from the stream, which is unforgeable-enough and matches the app's actual invariant; solve (ii) with a `selfId` lexicographic tie-break, which is deterministic, clock-free and symmetric. Reject Lamport/monotonic-timestamp "first claim wins": the loser must tear down a running emulator either way, so fairness-by-arrival buys nothing and adds a clock-skew failure mode.
Forecloses **nothing** about future control handoff — and that is the point of framing it this way. A guest gaining input authority does not need to become "host": the streamer stays the host, and "who may inject keys/clicks" becomes a separate, explicitly granted capability. Reserve UI space for it now (left of the chat titlebar [X], a per-row slot in the roster, the right end of any future control bar) and design nothing.

**(d) Does the chat own system events?**
**Recommendation: yes, as an event log; no, as a notification channel.** System lines give retrospective context and never move the unread badge (at most a dot). Notifications live in the status pill and short toasts. Say this out loud, because the audits disagreed on what chat-as-log actually buys — a host looking at the game sees nothing from a suppressed system line, and pretending otherwise leads to badge spam on every hiccup.
Forecloses: using the transcript as the primary presence surface, which is why (e) matters.

**(e) How much do we harden against a hostile spectator?**
**Recommendation: only the cheap invariants — badge and HOST_LEFT driven by the stream, not by a claim — and then tell the truth in the UI: the password is the boundary.** Share links deliberately omit the password (`room-code.helper.ts:22-28`) and get pasted into public group chats. No moderation tools, no kick, no admission checks. Leave a code comment where `makeAction(..., {kind:'request'})` and `onPeerHandshake` would allow a real admission check later.
Forecloses: any "public room" story that does not lean on the password.

#### As built — deviations from the plan above

Four changes were made during implementation. The items above are left as written; these override them.

- **The collision tie-break is age-based, not `selfId`-based** (item 3). A pure `selfId` comparison is deterministic and symmetric, but arbitrary with respect to *arrival*: in testing it tore down the established broadcast to preserve a brand-new one, which is strictly the worse outcome — an established room may have spectators mid-match while a newcomer has nobody. Each host now reports its own elapsed broadcast time (`hostingForMs`, from `performance.now()`), and the **older** host keeps the room. No shared clock is involved, so the clock-skew objection in §2.4 does not apply. Differences under `MULTIPLAYER.HOST_AGE_TOLERANCE` (2 s) are treated as simultaneous and still fall back to `selfId`, preserving determinism. The winner is notified on a dedicated `codeContested$`, not by reusing `intrusion$` with a misleading kind.
- **The a11y hit-target floor is opt-in** (item 7). Applying `min-height: 44px` to `.win9x-button` retrofitted a floor onto the existing Cheat 'O Matic buttons, growing them enough to overflow the modal into a scrollbar — a visible regression in a phase whose contract was zero visual change. The token remains as `--win9x-hit-target` and is applied only via `.win9x-button--touch`, which nothing currently uses. Phase 3 opts in deliberately, where the layout is designed around it. `:focus` was likewise kept rather than modernised to `:focus-visible`, for the same reason.
- **`maxlength` was removed from the room-code field entirely, not set to 8** (item 5). The two halves of that instruction conflict: any `maxlength` truncates a pasted share link before `sanitize()` can parse the code out of it. Validation is enforced by `isValid()` plus sanitising on `ionBlur` and in `confirm()` instead.
- **`waitForVideoStream()` was replaced by `videoStream$`** (item 4). The guest races the stream against `joinError$` with rxjs `race` inside a single `firstValueFrom`, so the timeout still applies and no subscription is left dangling when the other branch wins.

#### As built — Phase 2 deviations

**The overlay was built, tested on a phone, and reversed.** §3(b) argued for one
`transform`-animated overlay panel at every breakpoint on the grounds that a 4:3 canvas
leaves letterbox margin an overlay can sit on. The margin data was right; the conclusion
was backwards. On a 390x844 phone the shipped overlay left all **496px** of vertical
letterbox empty and put a 253px panel *on top of the game* — reported as "blank space at
the top" and "chat too thin", which were the same defect.

The margin is a **free docking budget**: a 4:3 frame in a non-4:3 box always leaves slack
on one axis, and spending that slack costs the canvas nothing. Measured:

| viewport | content | canvas (4:3) | fit | free |
|---|---|---|---|---|
| 390x844 portrait | 390x788 | 390x292 | width | **496px height** |
| 360x640 portrait | 360x584 | 360x270 | width | 314px height |
| 844x390 landscape | 844x390 | 520x390 | height | 324px width |
| 1920x1080 | 1920x1024 | 1365x1024 | height | 555px width |
| 1024x768 iPad ls | 1024x712 | 949x712 | height | only 75px width |

As shipped:

- **Portrait** — `.game-stream-flex-container` is a column; `.game-stream-container` is
  pinned to exactly the 4:3 box via `flex: 0 0 var(--game-box-height)` where
  `--game-box-height: 75vw` (a percentage of the *width*). The game therefore sits flush
  under the header with **no letterbox at all**, and the chat takes the remainder. Because
  the game box has a fixed basis, growing the chat cannot resize it — js-dos's resize
  detector never fires, so the reveal is safe to animate.
- **Landscape/desktop** — a row dock at `--chat-panel-width` (320px, `min(300px, 40vw)`
  under 900px). Here the canvas *is* height-fitted, so a panel wider than the margin does
  shrink it, at 1024x768-ish ratios. That is the accepted cost of docking; the width change
  is deliberately **not** transitioned, making it one re-letterbox per toggle instead of
  the ~18 the original animated sidebar caused.
- **The chat height must not be a percentage.** The first docked attempt used
  `height: max(0px, calc(100% - var(--game-box-height)))`. Sass silently stripped the inner
  `calc()`, and more importantly that `100%` is a percentage height on a flex item whose
  containing block is not reliably definite — it resolved to `auto`, and `app-chat`'s
  `:host { height: 100% }` then collapsed the panel to zero. The chat opened with no
  height, indistinguishable from not opening. It now grows with `flex: 1 1 0px` and the
  keyboard inset is a `margin-bottom`, so no percentage is on the growth path.
- `--kb-inset` moved from the overlay's `bottom` to shortening the docked chat; the game
  box is untouched either way.

## 5. Verification per phase

There are zero `.spec.ts` files, so everything below is manual. **Standing setup for every phase:** two browser contexts on the same machine — a normal window as host and a *separate profile or incognito* window as guest (`selfId` is per page load, and two tabs of one profile share IndexedDB, which will confuse save-state observations). Keep both devtools consoles open; several of these bugs are silent by design. Have `npm run lint` and `npm run build` green before manual testing — the component-style budget (2 kB warn / 4 kB error) is the one that will bite in phases 1 and 3.

**Standing regression checks, to run at the end of every phase.** These four are the ones that break silently:

- **Green-pixel load detection** (`game.page.ts:131-203`): cold-load `/game` with the cache cleared and confirm the loader dismisses on its own within ~10 s of the emulator appearing. It samples four hardcoded pixels from `dosCI.screenshot()` (the fixed render buffer), so *displayed* size changes cannot affect it — but confirm no phase accidentally changed the Windows 3.1 video mode or hid `#game-container` with `display:none`/`*ngIf` (a 0×0 box poisons the canvas layout and `captureStream`; the existing `opacity: 0.0001` trick exists for exactly this reason).
- **Tesseract OCR auto-save detection** (`emulator-control.service.ts`, `EMULATOR_CONTROL_CONFIG.DEFAULT_AREA_OF_INTEREST`): trigger an in-game save, watch for the "a gravar o jogo…" detection log and the follow-up persist. Same reasoning — it reads the render buffer — so the real risk is anything that changes the guest OS resolution or the game language, not layout. Verify once per phase anyway, and specifically after Phase 2 (the container geometry changes a lot) and Phase 5 item 2 (the teardown ordering touches the auto-saver).

## 6. Considered and rejected

- **`ion-modal` sheet as the mobile chat** — reaches the same "never resize `#game-container`" goal as a CSS overlay but requires `expandToScroll: false`, `.ion-content-scroll-host`, DOM-gating the sidebar and two hosts for one component; an L of untestable Ionic-internals coupling for no additional user benefit.
- **Framing `#game-container` in a Win9x window with a titlebar** — costs canvas pixels where they are scarcest, must wrap rather than nest, and renders in the system sans on most platforms. (Not, as an earlier draft claimed, because it changes the captured track resolution — see §2.2.)
- **Bundling a pixel webfont (W95FA) for body text** — hurts legibility for the text users read most, in a language full of accented glyphs at 12 px; also a licence question on a public site. Optional and display-only at best.
- **MSN nudge/buzz, animated emoticons and winks** — highest annoyance-to-value ratio in the set; the nudge would also risk shaking the emulator container. Ship only the unread flash on the toggle. Sound, if ever, as a WebAudio burst behind a stored preference — not an asset.
- **A `Reconectando…` chat system line and `O anfitrião encerrou a sala.` in the transcript** — unreachable: the same `leaveRoom` that produces them calls `chatService.clear()` in the same turn, and the sidebar is hidden by then. The state card already says it.
- **`interactive-widget=resizes-content`** — resizes the layout viewport, so `#game-container` resizes and js-dos re-letterboxes on every Android keyboard open: the exact jump we are removing, reintroduced.
- **Dropping `user-scalable=no` / `maximum-scale=1.0`** — re-enables iOS auto-zoom on every sub-16px input (chat field, room code, alert inputs), shifting the visual viewport mid-game. If tiny 1998 text is the problem, solve it with an in-app zoom control.
- **`getPeers()[peerId].connectionState` inside a peer-leave handler** — the peer is already removed from `activePeerMap` before `onPeerLeave` fires, so it reads `undefined`. Legitimate only for live degradation (§2.3 quality).
- **Auto-retrying `joinGameRoom` after a host drop** — throws `Already in a room` unless you leave first, which is what the grace period exists to avoid. The stream re-attach subscription is the actual fix.
- **`:focus-visible`-only focus rings on `.win9x-button`** — would remove the keyboard focus ring from every `ion-button` (shadow-encapsulated host does not match). An accessibility change that makes accessibility worse.
- **`border-left` on `.chat-sidebar-flex`** — `box-sizing: border-box` leaves a permanent 2 px grey sliver beside the canvas with the chat closed.
- **A slotted `ion-badge` inside an `ion-fab-button`** — clipped by `overflow: hidden` + `contain: strict` with no escape hatch; the count would ship invisible.
- **A leading ping in `MultiplayerPlayerInfoService.setup()`** — `setup()` starts with `clear()` and no remote peer exists yet, so it pings nobody. Ping on ident instead.
- **Persisting the room password (for "recent rooms" or host reload resume)** — a privacy regression on a shared device, and it would have to survive the data-wipe paths. Codes only.
- **Host session resume across a reload** — deferred, not rejected, but explicitly out of this plan: it needs new `STORAGE_KEY`s, a canvas-ready gate and a `Retomar a transmissão da sala {{código}}?` prompt, and the grace period does *not* cover it (nothing about hosting is persisted today, so a reloaded host is simply gone).
- **Control handoff** — out of scope by decision. The protocol reframing in §3(c) deliberately leaves room for it without designing it.
